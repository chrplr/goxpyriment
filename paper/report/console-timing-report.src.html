The display stack is the jitter

Five five-minute runs of one binary on one machine. Real-time scheduling bought a factor of 1.8. Rewriting the trigger path bought nothing at all. Changing which display stack the program talks to bought a factor of sixteen — and moved the latency by a whole frame in the bargain.

Trigger-to-photon interval, standard deviation across a five-minute block. Same executable, same panel, same night — only the display stack differs. For scale, the best figure in the published cross-package comparison is 0.18 ms.

All three runs drawn to scale on one axis. Xorg is the narrowest band and the latest one — the two are different quantities, and only one of them matters.

What is being measured, and which half of it counts

In EEG and MEG the TTL trigger is the timestamp. A constant delay between the trigger and the screen is harmless: measure it once, subtract it, lose nothing. Variation in that delay is not recoverable, because nothing in the recording says which trial was late.

So the two columns below are not equally important. The spread is the number that decides whether a paradigm is viable. The lag is bookkeeping — provided you know it, and provided it holds still.

Both signals go into a single acquisition on one instrument, so the instrument's clock cancels and never has to be reconciled with the host's.

Five runs, four hypotheses

Each run changed one thing. Two of the four predictions were wrong, which is the useful part — it rules out explanations that sound right.

  1. A

    Baseline — Wayland, normal priority

    The configuration most people actually run. sd 2.34 ms, the delay wandering between 14 and 39 ms across the block.

  2. B

    Real-time scheduling

    The late flips looked like preemption, so the same run under chrt -f 50. sd 2.34 → 1.32 ms with the mean unchanged: the signature of removing a delay that only happened sometimes.

    Confirmed · 1.8×
  3. C

    Synchronous trigger instead of a goroutine

    The harness fires its trigger on a separate goroutine; every package in the published comparison writes it inline. Predicted to be worth about a millisecond. Worth nothing — 1.344 against 1.320, in the wrong direction. This run logs its own flip-to-trigger gap, which settles it directly rather than by inference: median 11 µs, worst case 38 µs.

    Refuted · the trigger path was never the problem
  4. D

    No display server at all

    A bare Linux console, SDL_VIDEODRIVER=kmsdrm, nothing between the program and the hardware. sd 1.344 → 0.113 ms, and the mechanism disappears rather than shrinking: not one flip in 640 lands more than 1 ms off the frame grid, where Wayland misses on one trial in fifteen. But the mean fell only 2.8 ms, not the frame that was predicted.

    Confirmed for the spread · refuted for the lag
  5. E

    Bare Xorg with a non-compositing window manager

    The stack the published study actually used, and the one most labs still have: an X server with openbox and nothing else, exclusive fullscreen. The steadiest result of all — sd 0.083 ms, every one of 581 trials inside a 0.43 ms band — and simultaneously the latest, at a mean of 35.74 ms.

    Best precision measured · one extra frame of lag

So the program's flip returns one frame before the photons on bare hardware and two frames before them under X. Neither is the compositor's doing — the compositor added only the variance around it. That pattern is what you would expect if the call returns when a page flip is queued at one vblank while the content becomes visible at a later one, and the swap chain under X is one buffer deeper.

The panel put every one of 2951 stimuli on an exact frame boundary — median error 6 µs — in all five runs.

It was never the variable. Neither was the trigger: the host-side path from flip to TTL is under 40 µs in every condition. Everything measured here happens between the program asking for a frame and the program being told it happened.

Lag figures depend on where the sensor's threshold sits on the panel's 5.5 ms rise; these are the 10 % crossing.

Psychtoolbox's flip returns essentially at scanout. goxpyriment's returns two frames early. It costs nothing scientifically — the offset is constant to 83 µs and subtracts out of any analysis — but it is a software property, not a hardware one, and it is the only number in this whole investigation that looks reducible.

Where the second instrument stops being usable

Every run was recorded simultaneously by a second, unrelated instrument. For the first four it reproduced the primary instrument's standard deviation to three significant figures — 2.33 against 2.342, 1.32 against 1.320, 1.35 against 1.344, 0.17 against 0.113, the last at its own 250 µs quantisation floor.

For the Xorg run it does not, and it is not quoted. It reports 1.55 ms against 0.083, because seven trials read 24–28 ms where the primary instrument saw nothing below 35.52 ms in any of 581. Its optical threshold was never calibrated against this panel, and a threshold sitting high on a 5.5 ms ramp crosses erratically when the final luminance wobbles.

Agreement between two instruments is worth a great deal, right up to the point where one of them is misconfigured — and that point does not announce itself. It announced itself here only because the other instrument had 1 µs resolution and a threshold under explicit control.

What to do with this

If the timing has to be tight, do not run the experiment inside a compositor. On this hardware that is worth sixteen times more than every software change measured here put together, and either escape route works: a bare X server with a plain window manager, or a virtual console with no display server at all. Real-time priority is worth a further 1.8× and is one flag.

Measure your constant offset and write it down. It differs by a whole frame between two stacks on the same machine, so it is not a property of your hardware that you can look up. It is stable once measured — to 83 µs over five minutes — which is what makes it harmless.

Log the flip timestamp on every trial, and record the scheduling policy and the video driver alongside it. Two runs that differ in those and say so are comparable; two that differ and don't are not.

And measure your own rig. Everything here is one machine and one panel; the study's own authors decline to generalise across machines, and so should this.

This advice is portable — the console route is not

Running with no display server at all works here because SDL3 has a KMS/DRM backend that talks to the hardware directly. That is not general. PsychoPy renders through pyglet, and on Linux pyglet offers exactly two paths: xlib, or a headless mode built on EGL_PLATFORM_DEVICE_EXT — an offscreen device context that renders into a buffer nobody ever scans out. There is no DRM or GBM anywhere in it, and no Wayland backend either, so PsychoPy under a Wayland session is going through XWayland.

But the headline recommendation survives that, because bare Xorg is the better of the two configurations anyway, and it is available to everything. pyglet 1.5.27, checked in place; the Psychtoolbox and GLFW claims are reasoned from their architecture, not measured here.

Reproducing it

# bare Xorg, no compositor -- run from a text VT, openbox as the only client
export SDL_VIDEODRIVER=x11
xinit /path/to/wrapper -- :2 vt3      # wrapper starts openbox, then:
chrt -f 50 ./test_photodiode_latency -s 1 -no-prompt \
     -trials 640 -line 0 -diode all -patch 400 \
     -frames 12 -isi-frames 18

# or with no display server at all
SDL_VIDEODRIVER=kmsdrm chrt -f 50 ./test_photodiode_latency ...

# capture both channels on one instrument, then extract the onsets
./ad3-capture.py --channels 1,2 --seconds 300 --rate 2e5 \
     --range 5,50 --offset 2.5,25 --attenuation 1,10 \
     --save-raw --out run.npz
./extract-onsets.py run.npz onsets.npz
./plot-onset-sequence.py --out seq.png --title "..." "run=onsets.npz"
