What is being measured

In EEG and MEG the TTL trigger is the timestamp. A constant delay between the trigger and the screen is harmless — subtract it. Variation in that delay is not recoverable, because nothing in the recording says which trial was late. So the quantity that matters is the trial-to-trial spread of the interval from the trigger pulse to the pixels actually changing.

Both signals go into a single acquisition on one instrument, so the instrument's clock cancels and never has to be reconciled with the host's. A second, entirely independent instrument recorded every run at the same time; it agreed to three significant figures on every condition.

Four runs, three hypotheses

Each run changed exactly one thing. Two of the three predictions were wrong, which is the useful part — it rules out explanations that sound right.

  1. A

    Baseline — Wayland, normal priority

    The starting point, and the configuration most people actually run. sd 2.34 ms, with the delay wandering between 14 and 39 ms across the block.

  2. B

    Real-time scheduling

    The late flips looked like preemption, so the same run under chrt -f 50. sd 2.34 → 1.32 ms, with the mean unchanged: the signature of removing a delay that only happened sometimes.

    Confirmed · 1.8×
  3. C

    Synchronous trigger instead of a goroutine

    The test harness fires its trigger on a separate goroutine; every package in the published comparison writes it inline. Predicted to be worth about a millisecond. It was worth nothing — 1.344 against 1.320, in the wrong direction. The run logs its own flip-to-trigger gap, which settles it directly: median 11 µs, worst case 38 µs.

    Refuted · the trigger path was never the problem
  4. D

    No display server at all

    A bare Linux virtual console, SDL_VIDEODRIVER=kmsdrm, nothing between the program and the hardware. sd 1.344 → 0.113 ms, and the mechanism disappears rather than shrinking: not one flip in 640 lands more than 1 ms off the frame grid, where a Wayland session misses on one trial in fifteen.

    Confirmed for the jitter · refuted for the lag

The display was never the problem

Asking of each event train whether consecutive trials are separated by a whole number of frame periods separates the three layers completely, and the answer is the same in every run.

Photodiode intervals sit on a whole number of frames with a median error of 6 µs and a worst case of 169 µs, across 1779 trials and four runs, without a single exception. The implied frame period, 16.6557 ms — 60.0395 Hz — matches the 60.0400 Hz the driver reports, to 8 parts per million, from an instrument that knows nothing about the display.

The panel puts every stimulus on an exact frame boundary. The trigger meant to mark it is sometimes milliseconds late.

The trigger inherits that error because it is fired off the flip's return. Which is why the trigger code was never worth optimising: the host-side path from flip to TTL is under 40 µs in every run.

The one thing the console did not fix

The prediction going in was that removing the compositor would remove one frame of buffering, so the mean would drop by about 16.7 ms as well as the scatter. It didn't. The mean fell only 2.8 ms, from 21.75 to 18.91.

So goxpyriment still emits its trigger roughly one frame before the photons, with or without a compositor, and that frame is not the compositor's doing — what the compositor added was the variance around it. The residual is what you would expect if Update() returns when the page flip is queued at one vblank while the content becomes visible at the next: 16.66 ms plus about 2 ms of scanout down to the patch accounts for 18.9 almost exactly.

For EEG and MEG that distinction is the whole point. A constant 19 ms is subtracted in analysis and costs nothing. The 1.3 ms of scatter around it could not be.

The 0.17 ms figure is at the toolkit's 250 µs quantisation floor — it is reporting its own resolution. The 1 µs instrument says 0.113 ms. Several of the published 0.18–0.19 values are presumably at that same floor.

On a bare console this sits at the top of that table. Under Wayland it is worse than thirteen of the fourteen entries. Same binary, same machine, same night.

Which is worth remembering when reading anyone's row in it, including the published ones. That column describes a display stack at least as much as it describes a package.

Why an uncalibrated sensor does not undermine this

The toolkit's optical threshold was left at its default and never calibrated against this panel, which is why it reads 21.3 ms where the 10 % crossing on the other instrument reads 18.9. Sweeping the onset level across the panel's entire rise shows exactly what that can and cannot affect.

A 6 ms sweep of the threshold moves the mean by 6 ms and the sd by at most 0.02 ms.

So every precision figure here is insensitive to where either sensor's threshold sits, and every lag figure is not — quote a lag only with its level attached. The lag conclusion survives regardless: even at 5 %, the earliest defensible level, the console gives 18.31 ms against PsychToolBox Ubuntu's 4.53, and no threshold choice closes 14 ms on a panel whose entire rise is 6 ms.

What to do with this

If the timing has to be tight, do not run the experiment inside a desktop session. On this hardware that is worth twelve times more than every software change measured here put together, and it costs one boot into a virtual console. Real-time priority is worth a further 1.8× and is one flag.

Whatever you run, log the flip timestamp on every trial and put it in the data file, and record the scheduling policy and the video driver alongside it. Two runs that differ in those and say so are comparable; two that differ and don't are not.

And measure your own rig. Everything here is one machine and one panel; the paper's own authors decline to generalise across machines, and so should this.

A caveat on the advice: not every package can take it

Running with no display server at all is available here because SDL3 has a KMS/DRM backend that talks to the hardware directly. That is not a general property of experiment software.

PsychoPy renders through pyglet, and on Linux pyglet offers exactly two paths: xlib, or a headless mode built on EGL_PLATFORM_DEVICE_EXT — an offscreen device context that renders into a buffer nobody ever scans out. There is no DRM or GBM anywhere in it. Notably there is no Wayland backend either, so PsychoPy under a Wayland session is going through XWayland. It therefore cannot be run the way column D was run; the nearest equivalent is a bare X server with no window manager. The same is true of the GLFW backend. pyglet 1.5.27, checked in place; the Psychtoolbox and GLFW claims are reasoned from their architecture, not measured here.

Not yet tested

Xorg — the configuration the published comparison actually ran, and the one most labs still have. It sits somewhere between these two extremes and nothing here says where. Ubuntu 26.04 no longer ships an X11 desktop session, so that needs a bare xinit run or a different machine.

Reproducing it

# from a bare virtual console, no display server running
export SDL_VIDEODRIVER=kmsdrm
chrt -f 50 ./test_photodiode_latency -s 1 -no-prompt \
     -trials 640 -line 0 -diode all -patch 400 \
     -frames 12 -isi-frames 18

# capture both channels on one instrument, then extract the onsets
./ad3-capture.py --channels 1,2 --seconds 300 --rate 2e5 \
     --range 5,50 --offset 2.5,25 --attenuation 1,10 \
     --save-raw --out run.npz
./extract-onsets.py run.npz onsets.npz
./plot-onset-sequence.py --out seq.png --title "..." "run=onsets.npz"
