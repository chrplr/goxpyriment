# Shape Change Detection

An adult version of the two-stream change-detection paradigm used with infants
(Libertus & Brannon, 2010; Decarli, Piazza & Izard, 2023). The infant version,
with dot arrays and looking times coded by the experimenter, is
[`Number-Change-Detection`](../Number-Change-Detection/). Here the streams show
shapes, and the participant reports the change themselves.

## Procedure

Two streams of white shapes flash in synchrony on a black background, one on
each side of a central fixation cross: 500 ms on, 300 ms blank, up to 20 images
per trial.

- Both sides start with the same shape.
- On a **change trial**, one side starts alternating with a new shape at a
  random image (4 to 14): new, base, new, base, …
- On a **catch trial** (5 of the 25), nothing changes.
- The participant clicks any mouse button, or presses SPACE, as soon as they
  see a change. The trial ends at the first response, or at the end of the
  stream.

The shapes are a circle, a triangle, a square, a pentagon and a hexagon. All
have the same area at a given size, and every shape's size varies by ±20 %
from image to image, so neither size nor area signals the change.

Both streams are drawn in a single frame (one `stimuli.DrawFunc` per image) and
presented by the VSYNC-locked `stimuli.PresentStreamOfStimuliHooks`, so the two
sides cannot drift apart.

## Usage

```bash
go run ./examples/Shape-Change-Detection -w -s 1     # windowed, subject 1
go run ./examples/Shape-Change-Detection -s 1        # fullscreen
```

ESC quits; the trial in progress is not recorded. Timing, trial counts and
sizes are constants at the top of `main.go`, and the participant-facing text is
in `main()`.

## Data

One row per trial:

| Column | Meaning |
|--------|---------|
| `trial` | Trial number (1–25) |
| `change_side` | `left`, `right`, or `none` (catch trial) |
| `base_shape` | Shape shown on both sides before the change |
| `new_shape` | Shape that alternates in after the change (`NA` on catch trials) |
| `change_image` | Image at which the change starts, 1-based (0 on catch trials) |
| `n_images` | Length of the stream (20) |
| `responded` | `true` if the participant responded |
| `device` | `mouse`, `key`, or `none` |
| `resp_image` | Image on screen (or in its blank) at the response (0 if none) |
| `rt_ms` | Response time from the onset of the first changed image (hits only) |
| `resp_from_start_ms` | Response time from the onset of the first image |
| `outcome` | `hit`, `miss`, `anticipation` (response before the change), `false_alarm`, `correct_rejection` |
| `max_dur_err_ms` | Worst difference between an image's on-screen duration (`TimingLog.OffsetNS − OnsetNS`) and its nominal whole-frame duration, over the images shown. 0 to a fraction of a millisecond means no frame was dropped; about one frame (16.7 ms at 60 Hz) means one was |

Both response times are differences of SDL hardware timestamps: the input
event's and the onset flip's.

The same task built from pre-rendered canvases, with a discussion of the two
approaches, is [`demo_canvas_stream`](../demo_canvas_stream/).
