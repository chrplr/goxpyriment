Two Trigger Boxes, One Timebase

How far apart do an FT232H and a DLP-IO8 actually fire when a program tells them to fire together? Six runs on one oscilloscope acquisition, with the host's own timestamps recorded alongside — so the answer separates what the devices cost from what the software cost.

Dell Precision 5490 · Ubuntu 26.04 · kernel 7.0.0-30 Analog Discovery 3 @ 1 MS/s tests/test_triggers

Every TTL device in triggers/ had been characterised on its own. Nothing had ever put two of them on one timebase, so the claim that a USB write costs more than a local ioctl rested on runs made hours apart against different clocks. test_triggers removes the comparison problem by removing the second run: both devices are pulsed on one absolute schedule, and an instrument watching both channels reads the difference directly. Its clock cancels; nothing has to be reconciled with the host's.

179.4 µs
sd 5.7 µs · 322 pulses · three 60-second runs

The program's own contribution to that number is 0.03 µs (median), so essentially all of it is the hardware. It is not a constant you can calibrate once: two runs in six sat 40–50 µs higher.

The method

Fire on a deadline, not in a sequence

Each device gets its own OS thread, locked, at SCHED_FIFO priority. All threads wait on the same absolute deadline and busy-spin the last 1.5 ms into it. They are never woken through a channel, because a per-repetition broadcast would re-serialise exactly what is being measured. The garbage collector is suspended for the whole train.

Every pulse also records the host clock either side of both writes. That is what makes a skew attributable: subtract the moment the program issued each write, and what remains is the device. Without it, a descheduled thread and a slow trigger box look identical.

Three full-length runs agree on the median to within 4.9 µs. Two datasets sit far outside that cluster — one whole run, and the last quarter of another.

Why the DLP-IO8 is the late one is not mysterious. Its write is an ASCII byte that crosses USB to an FTDI bridge, spends 87 µs on a 115200-baud UART, and is then parsed by a PIC that moves the pin. The FT232H write is one MPSSE bulk transfer that sets the pins in hardware.

What was counter-intuitive: the FT232H's SetHigh call blocks 38.8 µs against the DLP-IO8's 26.9 µs, so on host-side cost alone you would predict the opposite ordering. Call duration measures how long the host was blocked handing the write over. It says nothing about when the byte reaches the pin.

Why the host timestamps matter

Four excursions that were never the hardware

Run 5 looked like it had a problem: four pulses beyond 220 µs and a scatter that grew through the run. All four were the scheduler, not the devices.

The same subtraction does not rescue run 3 or the tail of run 1. Those survive it, which is how we know the slower regime is real and not a scheduling artefact.

The comparison that matters for experiment code

Firing in sequence costs 24 µs and six times the jitter

Most experiment code that drives two boxes writes to one, then the other. Running the same train that way puts the second device's edge further out — by almost exactly the first device's write-call duration.

The last row is a finding in its own right. The DLP-IO8's write costs twice as much when the FT232H write is in flight at the same moment — concurrent writes to two USB devices interfere at the host. It shows on the wire too: device-only skew is 180.5 µs in parallel against 164.6 µs in sequential, so simultaneous firing does cost about 16 µs. That is an order of magnitude less than sequential firing costs, so the trade is still worth making.

A bug the measurement found

The FT232H fired a 51 ms pulse every time it was opened

One channel kept reporting 121 edges against the other's 120. The extra one arrived two seconds before the train, while the program was still printing its wiring table, and it was 51.25 ms wide.

From the moment MPSSE is enabled the FT232H's pins are inputs on the chip's internal pull-ups, so every AD line sits HIGH until something drives it. NewFT232H only configured the D-bus at the end of initialisation, after a 50 ms settle, a buffer purge and the sync handshake. Into an EEG or MEG amplifier that is a spurious trigger — code 0xFF on all eight lines — on every open.

The fix moves SET_BITS_LOW to the first thing after MPSSE is enabled, before the settle rather than after it — the settle is what costs the 50 ms. If the engine is not ready the bytes are discarded and the purge that follows clears the buffer before the sync handshake, so an ignored write costs nothing and a successful one saves 50 ms of signal. Four measurements say the engine does accept it that early.

The remaining 123 µs cannot be removed in software: the pins are pulled up from the instant the mode is set, and nothing host-side can act sooner than one USB transfer later. An amplifier that latches any edge needs a pull-down resistor on the D-bus.

What is not settled

The slower regime

Two datasets in six sat 40–50 µs above the baseline — the last quarter of run 1, and all of run 3. Both survive host-skew subtraction, so they are not the scheduler. Neither is explained by the FT232H fix: runs 3, 4 and 5 all used the patched library. Two occurrences is enough to know the regime exists and not enough to characterise it.

What moves with it: in those datasets the DLP-IO8's on-wire pulse width also degrades (sd 30 µs and 27 µs, against 11 µs when normal), while the FT232H's is untouched at 10–11 µs throughout. Width and skew degrade together, which points at one effect somewhere downstream of the write syscall on the DLP-IO8's path — USB scheduling, the FTDI bridge, or the firmware. Nothing here distinguishes between those three.

Anyone repeating this should also know the analysis has an internal check that passed every time: the AD3-versus-host clock drift, estimated independently from each device, agreed to better than 1 ppm in every run (−16.0 and −16.5 ppm; −17.0 and −17.9; −16.1 and −16.1).

For practice

What to do with this

  • A 180 µs offset between two boxes is harmless if you know about it. It is a fixed delay in the sense that matters for EEG and MEG — far below one display frame, and an order of magnitude below what the display stack contributes.
  • Do not carry a calibration between sessions. Two runs in six sat 40–50 µs off the baseline, on the same bench, minutes apart. Measure in the session you care about.
  • Fire from separate threads on a common deadline. It costs about 16 µs of USB contention and saves 24 µs of serialisation plus most of the jitter.
  • Record the host's timestamps beside the instrument's. Four of run 5's five worst pulses were the operating system, not the hardware, and nothing in the trace alone would have said so.
Reproducing it

The commands

# record both channels in one acquisition — close WaveForms first,
# it holds the AD3 exclusively
ad3-capture --seconds 75 --channels 1,2 --threshold 1.5 \
            --out ~/goxpy_data/run.npz

# 115 pulses + 5 warm-up at 500 ms = 60 s of train; press Enter at the prompt
go run ./tests/test_triggers \
    -device ft232h:pin=1 \
    -device dlpio8:port=/dev/ttyUSB1,pin=1 \
    -n 115 -isi-ms 500 -width-ms 5

# the same train issued from one thread, in flag order
go run ./tests/test_triggers -sequential \
    -device ft232h:pin=1 -device dlpio8:port=/dev/ttyUSB1,pin=1 \
    -n 115 -isi-ms 500 -width-ms 5

One absolute threshold of 1.5 V for both channels, deliberately: the FT232H swings 3.3 V and the DLP-IO8 5 V, so per-channel 50 % levels would sit at 1.65 V and 2.5 V and the difference would land straight in the skew. Grounds common between the devices and the instrument.

Data. Five parallel runs and one sequential, 21 August 2026, 16:12–17:03 local. Raw files: ft232h_vs_dlpio8*.npz (AD3 edge times) beside test_triggers_sub-999_date-2026082*.csv and their -info.txt sidecars, which carry the host facts, the mode, and every flag of each run.

Conditions. Parallel mode unless stated; SCHED_FIFO 50; GC suspended during the train; 5 warm-up pulses excluded from every statistic; pulses with a write error excluded — there were none. Run 2 (sequential) reported 60 810 corrupted samples and a 16 ms gap common to both channels; a common gap cancels in the channel difference, so skew is quoted from it and no per-channel time axis is.
