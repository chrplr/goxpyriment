Is the DLP-IO8 Fast Enough for MEG?

A USB trigger box is only usable if its lag is small and steady next to the parallel port everyone trusts. Nine hundred pulses, both boxes fired on one schedule and read on one oscilloscope acquisition, answer it: the DLP-IO8 is 0.19 ms behind, and never once came within four times the millisecond that matters.

Dell Precision 3650 Tower · i5-10600K · Ubuntu 24.04.4 · kernel 7.0.0-28 Analog Discovery 3 @ 1 MS/s tests/test_triggers

The parallel port is the reference every EEG and MEG lab reaches for: a write to it is an ioctl on a local chip, with no bus in the way. A DLP-IO8 costs a USB link, an FTDI bridge, 87 µs of 115200-baud UART and a microcontroller that has to parse the byte before it moves a pin. The question is not whether that costs something — it obviously does — but whether what it costs is small and repeatable enough to trigger a MEG recording with.

Both boxes were driven from the same absolute schedule, one locked thread each, and both edges were recorded in one AD3 acquisition. That is what makes the answer a measurement rather than a comparison of two sessions: the instrument's clock cancels, and the program records when it issued each write so that its own contribution can be subtracted rather than assumed.

Nothing exceeded 0.26 ms. Zero pulses past 500 µs, zero past 1 ms — a 3.9× margin. The program's own share of that number is 0.03 µs.

The host issued both writes within 0.03 µs (median, sd 1.63) across all 900 pulses, so essentially none of the 186 µs is the program or the scheduler. It is the box.

The five that are not in the pack

One of them is the parallel port's fault

Four of run 1's outliers are consecutive, t = 63.7–65.7 s, at +234 to +255 µs — the DLP-IO8 briefly running late and then recovering, the same behaviour seen on a different machine earlier the same day. Even at its worst that is a quarter of the budget.

The fifth is the interesting one. At t = 108.7 s the skew reads −51.9 µs, which would mean the USB box fired before the parallel port. It did not: the parallel pulse at that repetition is 4756 µs wide against a 4999 µs median, so its rising edge came ~240 µs late while its falling edge stayed on schedule. The host had issued the write on time (issue skew −0.04 µs), so the delay is below the syscall.

The reference is not perfectly deterministic either. Run 1 also reported 352 corrupted samples in the capture, so this single event cannot be separated from a misplaced edge — only edge times were saved, not the waveform. Either way it is worth knowing before treating the parallel port as ground truth: on this rig it produced one 240 µs excursion in 900 pulses, and the USB box produced four.
Cross-check

A second reference agrees to 6 µs

Earlier the same day, on a different machine, the same DLP-IO8 was measured against an FT232H instead of a parallel port: it lagged by 177–181 µs across three full-length runs. Here it lags a parallel port by 186 µs.

Those two references are independent — an MPSSE bulk transfer that sets pins in hardware versus an ioctl on a local chip — and they place the DLP-IO8 within about 6 µs of the same figure on two hosts, two operating-system versions, and two instruments' worth of wiring. Neither measurement was made to check the other, which is what makes the agreement worth something.

What this licenses

Use it, and subtract 0.19 ms

  • The lag is a constant, not noise. 186 µs with 12.6 µs of scatter. Against MEG sampled at 1 kHz that is a sub-sample offset: subtract it in the analysis and nothing is lost.
  • The jitter is what actually matters, and it is two orders of magnitude under a sample. A constant delay shifts every trial equally and averages out; only variability smears an average, and here it is ~13 µs.
  • Bounded, not just typical. Across 900 pulses the worst case was 255 µs. The claim being made is about the maximum observed, not the mean.
  • Fire from separate threads on a common deadline. Writing to one box and then the other, from one thread, costs the second box the first one's write duration — measured separately at +24 µs and six times the jitter.
Conditions, and what is not settled

Two caveats for anyone quoting this

The CPU governor was not pinned. The runs recorded host cpu_mhz of 3600, 3600 and 3256 against a 4800 maximum, so the clock was free to move. On this framework's display measurements an unpinned governor produced a clean mid-run regime change that no host-side statistic would have caught. A figure dominated by UART wire time should not care — but that is an expectation, and the way to settle it is a run with cpupower frequency-set -g performance, not an argument.

Real-time priority was requested, and the file records only the request. All three runs asked for SCHED_FIFO 50; the data files say what was asked for, not what the kernel granted. The pooled host issue skew — sd 1.63 µs — is strong evidence the threads did run real-time, but it is inference from the result rather than a record of the condition. test_triggers now reads the policy back with sched_getscheduler on each firing thread and records t realtime_obtained: beside the request, so the next run states it outright.

Also worth noting for a repeat: the capture ran on a second machine, so the two hosts' clocks cannot be aligned and no per-device host→wire latency is available here — only the channel-to-channel skew, which is the quantity the question actually asks about.

Reproducing it

The commands

# on the machine with the AD3 (close WaveForms first — it holds the device)
ad3-capture --seconds 180 --channels 1,2 --threshold 2.5 \
            --out ~/goxpy_data/parallel_vs_dlpio8_run1.npz

# on the machine with the two trigger devices
lsmod | grep '^lp' && sudo rmmod lp     # or the parallel claim can hang the box

go run ./tests/test_triggers -no-prompt \
    -device parallel:pin=1 \
    -device dlpio8:pin=1 \
    -n 300 -isi-ms 500 -width-ms 5

One absolute threshold of 2.5 V for both channels: both devices swing 5 V, so mid-swing is the same fraction of each edge. CH1 on DB25 pin 2 (D0), CH2 on terminal 1 of the DLP-IO8 block, and both grounds are the desktop's — the box is USB-powered from it, so there is one reference.
